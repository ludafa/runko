# 挂起与恢复（使用手册）

> 相关：[技术方案](../tech/suspend-resume.md)，[施工进展](../plans/suspend-resume.md)。
> 依赖/延续：[轮编排运行时](./agent-runtime.md)（[轮](../../../terms.md)的一生、`submitDecision`）· [多副本部署](../../../host/node/features/multi-replica.md)（等人时释放[归属](../../../terms.md)正是这一批的收益来源）· [沙盒保活](./sandbox-keepalive.md)（[审批保活预算](../../../terms.md)是内存窗口的默认值来源）· [停止本轮](./turn-abort.md)（挂起是第四种收尾，与中断并列）。

## 1. 要解决的问题

**今天「等人」有两个硬毛病，根子是同一个：等待这件事只活在一个进程的内存里。**

### 毛病一：等人有条 4 分钟的死线

agent 要执行 `rm -rf build/`，弹出[审批卡片](../../../terms.md)。人去开了个会，25 分钟后回来 —— 卡片已经废了。框架 240 秒没等到，按**拒绝**处理。

`ask-user` 提问同理：240 秒后塞给模型一句英文提示「用户没回应，你自己看着办」，模型只好瞎猜着往下跑。

240 秒这个数字不是随便定的（它是沙盒 300 秒空闲超时的 80%），但**对人来说太短了**。真实的审批场景是「我看一眼、想一想、也许去问个人」，分钟级起步。

### 毛病二：等人期间机器放不掉

那一轮一直占着两样东西：[租约](../../../terms.md)（这个会话归我）和沙盒（连着的那台机器）。

于是滚动发布卡住：三个副本要换版本，其中一个上面有会话正在等人。要么等（不知道等多久），要么硬杀（用户回来发现这一轮显示「已中断」，白等了）。

### 加起来是什么感觉

| | 现在 | 本功能之后 |
|---|---|---|
| 人 4 分钟内没点审批 | 当作**拒绝**，这一轮带着「被拒绝」往下跑 | 这一轮**挂起**；人几小时后点「允许」，命令照常执行 |
| 人 4 分钟内没答 `ask-user` | 模型收到「没人回应」，自己瞎猜 | 同上，挂起等着 |
| 等人时要滚动发布 | 卡住，或者硬杀掉这一轮 | 直接挂起，pod 立刻可退 |
| 等人时那台沙盒 | 一直续着，烧钱 | 放掉；人回来重新唤醒（多等几秒） |

## 2. 一句话

> 等人等过一个窗口，就把这一轮**落盘退出、放掉机器**；人几小时后回来答，在**任意一个节点**接着干。

这就是[挂起](../../../terms.md)。它是**无损的**——账本、[裁决](../../../terms.md)、沙盒快照都还在，用户回来的代价只是多等几秒唤醒沙盒。

## 3. 用户会看到什么

三条时间线，取决于人多快回来：

### 3.1 窗口内点了（默认 5 分钟内）

**跟今天一模一样。** 这一轮直接往下跑，人感觉不到有「挂起」这回事存在。

大部分审批都落在这一档——人就在页面前面，看到卡片就点了。

### 3.2 一直没点

```
第 4 轮：  用户提问 → 模型思考 → 跑了两条命令 → 弹出审批卡片
          ⏳ 等 5 分钟 ……没人点
          💤 已挂起（进度落盘、归属释放、沙盒放掉）
```

界面上第 4 轮以「**已挂起**」收尾。审批卡片**还在那儿，还能点**——它不再有过期这回事。

那个节点这时已经空出来了，可以正常参与滚动发布并退出。

### 3.3 人回来点了

```
（3 小时后，也许是在另一台机器上的另一个副本）
第 5 轮：  结清那次调用 → 执行 rm -rf build/ → 「清理完了，删掉 234MB」
```

**恢复算「新的一轮」**，不是第 4 轮续着跑。所以界面上会看到两条轮记录。

### 3.4 挂起期间又发了一条消息

人还没答审批，又发了一条「顺便看看 README」。

**这条消息会排队，等你先答完那个审批。** 你点了「允许」之后，第 5 轮先把命令跑完、模型看完结果，收尾时才轮到这条。

这跟「同一轮里等人」的体验一致：agent 在等你回答一个问题，你不回答，它就没法往下走。

**想「不答了，直接干别的」，就先点拒绝。** 框架不会把「你发了新消息」擅自当成「你拒绝了」——你可能只是想插一句话。

> 为什么不能两边同时跑：agent 的历史里有一个「发出去了、还没有结果」的调用，模型服务商（Anthropic、OpenAI 兼容的都一样）会直接拒绝这样的请求。详见[技术方案 §5.3](../tech/suspend-resume.md)。

**等卡片的那几分钟里用「插话」发的消息也一样**：这一轮挂起时它还没来得及插进去，会自动转进待发队列，等你答完之后发出，不会丢。

### 3.5 同一步里排在它后面的操作，先不做

模型有时一口气发出好几个操作，比如「先删掉 dist 目录（要你审批），再往 dist 里写一个配置文件」。审批一挂起，**后面那个写文件就先不做**，模型会看到一句「没有执行，因为前一个在等人」。

这是为了保住顺序：要是后面的先做了，你几小时后批准「删掉 dist」，刚写进去的文件就被一起删了。你答完之后，模型看得到哪些没做，需要的话会重新发出。

（一批操作**全是只读的**，比如同时读几个文件，就没有顺序问题，照常并行做完。）

## 4. 两条轮记录是有意的

模型看到的历史仍然是连续的（`tool_use` 后面紧跟 `tool_result`），**轮号只是我们自己的记账**。

这样做换来一件实在的好处：**轮统计不会骗人**。

| | 一轮到底 | 拆成两轮（本方案） |
|---|---|---|
| 界面显示 | 「这一轮耗时 3 小时 5 分」 | 「第 4 轮 3 分钟」「第 5 轮 2 分钟」 |
| 人看了会以为 | agent 算了 3 小时 | agent 算了 5 分钟，中间等了我 3 小时 |

归属、单轮保活上限、[轮检查点](../../../terms.md)、前端「正在干活」指示——一样都不用为挂起重新定义。

## 5. 恢复时跑的是账本里原封不动的那条命令

这一条是**安全性质，不是实现细节**。

人批准的是「`rm -rf build/`」。恢复时框架从[账本](../../../terms.md)里把那次调用的参数原样取回来执行。

**不能走「告诉模型你被批准了、你再发一次」那条路**——模型这次可能发出 `rm -rf /`。用户批准的和实际跑的不是同一条，审批闸门就等于没有。

## 6. 怎么配

```ts
const runtime = createAgentRuntime({
  agent, prepareTurn, persistence, arbitration,

  suspend: {
    memoryWindow: "5m",       // 内存里先等多久，等不到就挂起。0 = 立刻挂起
    onPresence: "extend",     // 上报「人还在」时延长这个窗口
  },
});

// 页面心跳说「人还盯着这条会话」时调它（同步、不落库）
runtime.reportPresence(conversationId);
```

两个参数，都是**产品决策**，配错了最多是行为不符合预期，不会写坏数据。

`memoryWindow` 写毫秒数，或带单位的字符串（`"300ms"` / `"30s"` / `"5m"` / `"1h"`）。写错了（负数、单位不认识）`createAgentRuntime` 直接报错，不会悄悄按默认跑。

旧参数 `human.approvalTimeoutMs` / `human.askUserTimeoutMs` 还能用，但已废弃：配了照样生效（前者只管审批、后者只管提问），日志里会多一行提示。

### 6.1 `memoryWindow`：先在内存里等多久

**为什么要有这个窗口，而不是一律立刻挂起**：挂起再恢复要走一遍「落盘 → 释放归属 → 重新抢归属 → 唤醒沙盒」，几秒起步。而绝大多数审批人在几十秒内就点了。为这部分人付那几秒不划算。

默认 5 分钟，沿用[审批保活预算](../../../terms.md)——那正是「沙盒还愿意为等人续多久」的预算，两者对齐才不会出现「沙盒已经休眠了但框架还在内存里等」。

| 配什么 | 什么时候用 |
|---|---|
| `"5m"`（缺省） | 长驻进程（Node / 容器 / k8s） |
| `0` | Vercel Functions 那一档——实例随时被回收，在内存里等没有意义 |
| 更长（如 `"30m"`） | 单机自用、机器不会被回收，想省掉唤醒沙盒那几秒 |

### 6.2 `onPresence`：人还盯着的时候别急着挂

宿主可以上报[在场](../../../terms.md)（「此刻这个用户正盯着这条会话」）。配成 `"extend"` 时，每收到一次上报就把窗口往后推。

**前提是这个上报必须基于真实的交互事件**（页面可见 + 窗口聚焦 + 路由停在这条会话），不能是「TCP 连着」。连通性不代表人还在——半夜挂着页面睡着的浏览器会让会话永远不挂起。

不想接这套就配 `"ignore"`，窗口固定。

## 7. 四档宿主上的差别

| 部署形态 | `memoryWindow` | 说明 |
|---|---|---|
| 单进程 / cluster / 容器 / k8s | `"5m"`（缺省） | 节点可寻址，内存窗口内的裁决直接送到持有者手上 |
| Vercel Functions | `0` | 不可寻址、实例随时回收 → 等人一律立刻挂起，裁决落库，恢复时读 |
| Cloudflare Durable Object | `0` | 同上。DO 没请求时会被驱逐，内存等待留不住 |

**换档只动这一行配置**，业务代码（`enqueue` / `subscribe` / `submitDecision`）一个字不改。

## 8. 范围与非目标

### 做的

- 等人（审批 + `ask-user`）超过窗口 → 挂起。
- 人回来提交裁决 → 在任意节点恢复，起新的一轮。
- [交权](../../../terms.md)（滚动发布、缩容、`SIGTERM`）时若正在等人 → 立刻挂起，不等窗口走完。
- 挂起那一轮以 `suspended` 收尾，界面能认出来。

### 不做的

- **不是 durable execution。** [挂起点只有一个](../../../architecture/features/agent-kernel.md)：正在等人。那是唯一的干净边界——没有命令在跑、模型没在流式输出、沙盒也没在动。命令跑到一半切不了，因为不知道它跑完没有。
- **崩溃仍然按老路走。** 进程被强杀（OOM、`kill -9`）不走挂起，它没停在干净边界上。下次启动补一条「已中断」，跟[优雅关闭与崩溃恢复](./graceful-shutdown.md)一致。
- **不设挂起总上限。** 挂起是无损的，不需要超时兜底。真要腾机器直接交权即可。
- **框架不替你决定「谁能答」。** 谁有权点这个审批、几个人点算数，是宿主的产品决策。

## 9. 成功标准

1. **等人不再有死线**：审批卡片挂 3 小时后点「允许」，命令照常执行，且执行的是账本里原封不动的参数。
2. **等人不占机器**：审批挂起后那个节点能正常参与滚动发布并退出；人回来**在另一个副本上**恢复成功。
3. **窗口内无感**：5 分钟内点的审批，行为与今天完全一致（不多一次落盘、不多一次沙盒唤醒）。
4. **轮统计不骗人**：挂起那轮的耗时是「起轮到挂起」，不包含等人的 3 小时。
5. **换档只改一行**：`memoryWindow: 0` 就能在不可寻址的宿主上跑通同一套。
