# agent 内核包 `@nimbo/agent`（施工进展）

> 相关：产品/使用视角见 [feature.md](./feature.md)，技术方案见 [tech.md](./tech.md)。
> 设计讨论的完整记录（含被推翻的路线）在 [issue #2](https://github.com/ludafa/nimbo/issues/2)。

## 状态

**设计已收敛，代码未开工**（2026-08-09）。三份文档刚落地，术语待登记，阶段拆单如下。

**起因**：`apps/node-server` 只绑 SQLite、只跑单进程。作为 demo 够用，作为框架不够——别人拿 nimbo 建产品，得把「会话怎么接下去 / 等人怎么办 / 崩了怎么办 / 多进程怎么办」四件事重写一遍，而其中第四件很难写对，写错是静默的数据损坏。

### 排序依据

- **K1 排在最前**，因为「进行中草稿放内存」会打掉现有的孤儿轮判据，必须同时补上起轮标记——而起轮标记就是归属表的最小形态，K6 直接长在它上面。
- **K2 的验收标准是「零配置能跑」**：不配任何外部件就能起会话、跑完一轮、再跑下一轮。这条守住了，后面每一步都只是「换掉一个内置实现」。
- **K5 与 K6 同包但分两次 ship**：K5 只做持久化、行为零变化；K6 才引入 CAS 与租期标识。混做的话之后每个诡异现象都要先分辨是谁的锅。
- **K7 放在 K6 之后**：chat 应用是第一个真实宿主，它迁移成功才算接口经得起用。
- **K9 里 `stream-redis` 只有 ④b Vercel 一档需要**，其余要么单进程、要么能转发、要么平台自带，所以排最后。

## 从 chat 应用吸收（2026-08-10 逐条对照）

文档按分层重排时，把 [app 层](../../app/README.md)（`apps/node-server` + `apps/web`）已实现的能力和本方案逐条比了一遍。两条处理规则：

> **目标一致的 → 以本方案为准**，chat 应用那份降级为「现状实现」，设计权威在本目录。
> **chat 应用有、本方案没有的 → 记进下面表 B**，明确归哪层、什么时候接。

### 表 A：目标一致，以本方案为准

app 侧对应章节已就地标注「设计权威在 agent 层」，下面只列**现状与本方案不一致、迁移时必须改**的地方。

| 能力 | chat 应用现状 | 本方案 | 何时收敛 |
|---|---|---|---|
| **等人的上限** | 审批卡片 240 秒超时**自动按拒绝处理**（`CHAT_APPROVAL_TIMEOUT_MS`），走与人点「拒绝」完全同一条路 | 内存窗口（默认 5 分钟）等不到就[挂起](../../terms.md)，人几小时后回来照样能裁决——**没有「N 分钟就作废」这回事** | K3 |
| **进程重启** | 进行中那一轮一律按中断收尾（[优雅关闭](../graceful-shutdown/feature.md)让它如实交代，不再静默卡住） | **正在等人**这一个干净边界改为挂起 + 任意节点恢复；被强杀仍走中断老路 | K3 |
| **账本条目种类** | `conversation_events` 两种 `kind`：`message`（完工）+ `chunk`（进行中那轮的耐久帧，收尾时 GC） | 账本只有完工消息一种；[进行中草稿放内存](../in-flight-draft/tech.md)，`chunk` 行整类消失 | K1 |
| **seq 怎么分配** | `MAX(seq)+1`（`store.ts` 的 `getMaxEventSeq`），跨重启从库里续 | 由[归属仲裁](../../terms.md)分配（租约表水位 + CAS），**允许空洞**；`MAX(seq)+1` 是方言特性，通用适配器表达不了 | K6 |
| **待发队列存哪** | 会话行上的 `queued_messages_json` | 独立的 `QUEUED_INPUT`，模型归轮编排、存储归宿主层；出队与释放归属之间的竞态由框架处理一次 | K4 |
| **谁在驱动一轮** | 进程内 `Map<conversationId, ActiveTurn>`（`turn-runner/registry.ts`），单进程独占是隐含前提 | 同一件事叫[归属仲裁](../../terms.md)，单进程版就是内存里一个 Map——**接口上必须留出「写入被拒绝」这条正常路径**，否则换租约版就是静默数据损坏 | K2 / K6 |
| **断线续传的流** | `GET .../stream?after=<seq>`：先订阅后回放、过程帧不占 seq、回放期 ephemeral 丢弃 | 语义原样继承进[流分发](../../terms.md)契约（`subscribe(id, { after })` 吐中立帧，序列化仍归构建者） | K2 |
| **沙盒生命周期** | `sandbox-manager.ts` 的三态 `acquire` + `touch` 续期 + 平台快照休眠 | 生命周期归轮编排管，沙盒本身是宿主层资源（[保活](../../host/sandbox-keepalive/feature.md)的信号从轮编排发） | K2 / K7 |

### 表 B：chat 应用有、本方案还没有（待补）

| 能力 | 现状在哪 | 归哪层 | 怎么处理 |
|---|---|---|---|
| **ask-user 提问通道** | `human-bridge.ts` 的 `pendingQuestions`，独立于审批；超时 240 秒返回一句固定提示 | **agent 逻辑层**（漏了） | 本方案的「人」只设计了审批裁决一条通道，但 ask-user **同样是等人**，同样该走挂起/恢复。K3 要一并覆盖：裁决模型不能只能表达 allow/deny，得能表达「一段回答」。**见下「还没定的」6** |
| **可复用的授权（grant）** | `conversation_grants` 子表 + [分段授权](../../app/approval-grant-split/feature.md)（按[命令段](../../terms.md)记账） | **agent 逻辑层**（漏了）+ 键的算法归构建者 | 本方案 §3 的 `DECISION` 只记「**某一次调用**被批了/被拒了」；`scope: 'broader'` 记下来之后**怎么复用、怎么查**是空白的——而这条授权恰恰是[跨执行的状态](../../terms.md)（下一轮、甚至下次重启还要命中），按判据二它就该由轮编排定义模型、宿主层负责存。**分界**：框架管「存一条 grant、按键查有没有命中」，**构建者管「键怎么算」**（框架不该懂 bash 语法）。见「还没定的」7 |
| **该通知人的时刻** | [推送通知](../../app/push-notification/feature.md)自己在四个时刻投递（要审批、要回答、轮结束、失败） | 框架发信号，投递归构建者 | 框架不做通知，但**必须把这四个时刻作为可订阅的信号发出来**——现在 chat 应用是从内部实现里就地取材的，迁移后拿不到。K2 定接口时一并留口 |
| **presence 上报** | `POST .../presence` + 前端只在真实交互事件上报 | 接入层（已在本方案 §3 端点④） | 已有设计，无需补；但要在文档里写死「不能拿 SSE 还连着当在场数据」这条硬要求（feature.md 已写） |
| **轮级统计与遥测** | `metadata.durationMs`/`toolDurationMs`/token 四分（账本里）+ 独立遥测库（[telemetry](../../app/telemetry/feature.md)） | 账本部分归轮编排，落库归构建者 | 轮的耗时/用量是**轮编排收尾时**产出的，框架要负责写进账本 metadata；遥测的存储与查询留在构建者侧。K2 定 `finalize` 时一并定 |
| **非账本的状态帧** | [轮状态快照](../../terms.md)（`turn-state`）与队列快照——**无 seq、不落库、不进账本**，每条连接都发一次 | 流分发契约 | `subscribe` 的帧类型现在只考虑了账本帧。这两类「此刻状态长这样」的帧要进契约，否则前端又要回去猜。K2 |
| **审批卡片何时算「已失效」** | web 侧从账本结构推导（轮收尾 ⇒ 挂起项必然已结） | 接入层（构建者） | 挂起/恢复上线后**这条推导会失效**：挂起的那一轮已经收尾了，但它的裁决仍然有效、还在等人。K3 要给出替代判据（按裁决行的 `decidedAt` 是否为空，而不是按轮活没活） |
| **应用侧的会话数据** | `title`/`repo`/`branch_name`/`sandbox_name`/`status`/属主与登录态 | 构建者，**明确不进框架** | 本方案 §9 已列为非目标：nimbo 只认不透明的 `conversationId`/`ownerId`，不做外键、不标准化 chat 的数据模型 |

- **两块**：agent 逻辑层、宿主层

- **其余**：租期标识（lease token）、跨执行的状态、挂起、等人状态、交权、conversation-drained

### 期间被推翻的判断

留个底，免得再走一遍：

| 曾经的说法 | 后来 |
|---|---|
| 「用户可能几小时后才回来点允许，promise 就 await 在那儿」 | **与代码不符**——现有实现 240 秒自动拒绝。真问题是「上了推送之后这个上限要不要放长」 |
| 「Vercel 出局，因为等不了人」 | **理由两次被推翻**，最终结论是 Vercel **成立**——只有实时流真需要寻址，而流可以外挂 Redis Streams |
| 「E2B Pro 24 小时是硬上限，隔一天回来沙盒就没了」 | 那是**连续运行**上限；暂停后无限期保存、不计费 |
| 「栅栏令牌必须单调递增」 | 校验是**等值判断**，只需唯一——改用调用方生成的 ULID，省掉 `RETURNING` |
| 「CAS 是存储契约的硬要求」 | **层放错了**——它是租约版归属仲裁的要求，用 DO 的人根本不碰 |
| 决定 17「待发队列归宿主」 | **被决定 24 推翻**。它把「要不要这个功能」和「怎么实现」混成一件事，还自己制造了一个跨存储竞态 |
| 「记录自成一层」 | 持久化**贯穿整个逻辑层**，不该是一层；账本/裁决/队列的模型归轮编排，存储归宿主层 |

## 还没定的

1. **阶段划分要不要按新分层再排一次**——上面 K0–K9 是这次重排的结果，取代了 issue 里原来那张 0–4 的表。
2. **`in-flight-draft.md` 附录 D（成品边跑边存）要不要并进 K1**。澄清：**挂起不需要它**（挂起是主动的、停在干净边界，可以一次性写下当前进度），附录 D 是为**崩溃**准备的持续写入。两者不是一回事。
3. **core 的「恢复开轮」入口怎么加**（K3 的直接依赖）：扩展 `stream` 的入参（破坏性）还是并列一个 `settleAndRun(callId, result)`（推荐）。
4. **收尾状态加第四种 `suspended`**（现有 `completed`/`failed`/`interrupted`）——挂起是主动、可恢复的，不该显示成「已中断」。基本没争议，备案。
5. **挂起裁决记录里「会话内都允许」要不要单独成一个结局值**——倾向用 `scope: 'once' | 'broader'`，nimbo 只知道「比这一次更宽」，不定义宽到哪。
6. **ask-user 算不算第二种「等人」**（表 B 第 1 行）。它跟审批的差别只在**答案的形状**：审批答 allow/deny，提问答一段自由文本。倾向**合并成一件事**——挂起/恢复那套机制原样复用，裁决记录的 `outcome` 从两值放宽成「一个不透明的结果载荷」。真要分成两条通道，就得把挂起、恢复、超时、卡片失效各写两遍。
7. **可复用的授权（grant）在数据模型里长什么样**（表 B 第 2 行）。三个小问题：**要不要独立成表**（还是给 `DECISION` 加一列「这条授权的键」）；**键谁算**（倾向构建者算完透传给框架，框架只当不透明字符串存查——否则框架要懂 bash）；**作用域到哪**（chat 现在是「本会话 + 本用户」，框架应该只提供存查、由构建者决定键里带不带 userId）。
8. **恢复后的轮边界怎么呈现**。本方案说恢复算新的一轮、界面会看到两条轮记录（第 4 轮以「已挂起」收尾、第 5 轮从「结清那个调用」开始）；chat 现状**刻意去掉了「第 N 轮」分割线**（单账本连续渲染，[chat-ui](../../app/chat-ui/feature.md) 只留轮结果条与统计按钮）。两者不冲突但也没对齐——挂起态至少要有一个用户看得懂的落点，K3 前定。
