### 排序依据

- **K1 排在最前**，因为「进行中草稿放内存」会打掉现有的孤儿轮判据，必须同时补上起轮标记——而起轮标记就是归属表的最小形态，K6 直接长在它上面。
- **K2 的验收标准是「零配置能跑」**：不配任何外部件就能起会话、跑完一轮、再跑下一轮。这条守住了，后面每一步都只是「换掉一个内置实现」。
- **K5 与 K6 同包但分两次 ship**：K5 只做持久化、行为零变化；K6 才引入 CAS 与租期标识。混做的话之后每个诡异现象都要先分辨是谁的锅。
- **K7 放在 K6 之后**：chat 应用是第一个真实宿主，它迁移成功才算接口经得起用。
- **K9 里 `stream-redis` 只有 ④b Vercel 一档需要**，其余要么单进程、要么能转发、要么平台自带，所以排最后。
- **K10 排在 K3 之前**：挂起与恢复本身要发一批新事件（挂起、唤醒、在别的节点恢复）。先有事件层，K3 直接用；反过来的话 K3 先按旧的 `Logger` / `RuntimeHooks` 埋一遍，K10 再全部返工。
- **K11 与 K9 同期**：调用链要落在具体宿主上，Cloudflare 与 Vercel 两档的宿主包都还不存在。

### 期间被推翻的判断

留个底，免得再走一遍：

| 曾经的说法 | 后来 |
|---|---|
| 「用户可能几小时后才回来点允许，promise 就 await 在那儿」 | **与代码不符**——现有实现 240 秒自动拒绝。真问题是「上了推送之后这个上限要不要放长」 |
| 「Vercel 出局，因为等不了人」 | **理由两次被推翻**，最终结论是 Vercel **成立**——只有实时流真需要寻址，而流可以外挂 Redis Streams |
| 「E2B Pro 24 小时是硬上限，隔一天回来沙盒就没了」 | 那是**连续运行**上限；暂停后无限期保存、不计费 |
| 「栅栏令牌必须单调递增」 | 校验是**等值判断**，只需唯一——改用调用方生成的 ULID，省掉 `RETURNING` |

## 已定案（2026-08-22）

原来这里的五条**全部定案**，逐条如下。11 个问题的完整定案与理由见[轮编排运行时 · 施工进展](../../logic/orchestration/plans/agent-runtime.md)。

1. **阶段划分要不要按新分层再排一次** —— **关闭**。上面 K0–K9 那张表就是重排的结果，本批走掉四个（K1/K2/K4/K7），已经受过一次真实施工的检验。
2. **`in-flight-draft.md` 附录 D（成品边跑边存）要不要并进 K1** —— **关闭，但改写成一条独立待办**（见下）。这个问法已经失效：K1 早已交付，挂在它名下没意义了。
3. **core 的「恢复开轮」入口怎么加** —— **选 B：并列一个 `settleAndRun(callId, decision)`**，`stream()` 签名一个字不动。K3 的前置就此解开。理由（语义不同不该挤一个入口 / 纯新增 vs 破坏性）见轮编排那份的「Q1」。
4. **收尾状态加第四种 `suspended`** —— **加，而且现在就加**，不等 K3。已落地：core `RunkoMessageMetadata.status`（含 zod）、`@runko/agent` `TurnStatus`、node-server `TurnEndStatus`。**目前没有产出方**——`finalizeTurn` 至今只产出前三态，先加是为了让宿主/界面提前占好渲染分支。
5. **「会话内都允许」要不要单独成一个结局值** —— **定为 `scope: 'once' | 'conversation'`**（原落地的 `'broader'` 就此更名），**框架只记、不执行**。`session` 这个候选被否——它作为「聊天会话」的叫法 2026-07-17 已正式退役。完整理由见轮编排那份的「Q4」。
