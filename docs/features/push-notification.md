# 推送通知（push notification）

> 本文用到的术语见 [docs/terms.md](../terms.md)。
> 技术方案见 [docs/tech/push-notification.md](../tech/push-notification.md)，施工进展见 [docs/plans/push-notification.md](../plans/push-notification.md)。
> 相关功能：[审批](./chat-webapp.md)（要审批的那一刻）·[停止与排队](./steer-and-queue.md)（一轮怎么算结束）·[chat 界面](./chat-ui.md)（铃铛开关放哪）

## 1. 要解决什么问题

**一句话：agent 停下来等你，你却不知道。**

chat 里的一轮是**后台跑的**——你发完消息，浏览器关了、切去写代码、锁屏出门，服务端照样在跑。这本来是优点，但它带来两个具体的坏结果：

**第一，agent 停下来等你批准，而你不在。** 它要跑一条 `rm -rf build`，弹了审批卡片，然后**整轮挂住**。你回来才发现它已经卡了半小时。更糟的是[审批有超时](../tech/push-notification.md)：没人应答就自动拒绝，agent 只好带着一个"被拒绝"的结果继续往下走，做出来的东西完全不是你想要的。

**第二，一轮跑完了没人告诉你。** 长任务动辄十几分钟。现在只有两种办法知道它跑完没：一直盯着页面，或者过一会儿手动刷一下。前者浪费你的时间，后者浪费 agent 的时间——它可能十分钟前就跑完了。

这两件事的共同点是：**值得打扰你的时刻，系统是知道的，只是没有一条路把它送到你面前。**

## 2. 谁会用到

| 用户 | 场景 |
|---|---|
| 一边让 agent 跑活、一边干别的事的人 | 主要目标。发完消息就切走，靠通知叫回来 |
| 手机上盯着长任务的人 | 出门在外，任务还在跑，需要在手机上批准一条命令 |
| 开了好几条会话并行跑的人 | 页面一次只能看一条，另外几条出了事全靠通知 |

**只在一条会话上、全程盯着屏幕的人不需要它**——审批卡片就在眼前，通知只会重复打扰。这种情况下系统会[自动闭嘴](#34-你正盯着的那条会话不会打扰你)，不需要你手动关。

## 3. 你会看到什么

### 3.1 开启：点一下铃铛

页面右上角有个铃铛。第一次点它，浏览器弹出「是否允许 nimbo chat 发送通知」，点允许就完成了。

```
┌──────────────────────────────────────────────┐
│ nimbo / chat        Chat      🔔  ☀  Sign out│
│                     ↑                        │
│                     点这个                     │
└──────────────────────────────────────────────┘
```

铃铛有三种样子，一眼看得出当前状态：

| 样子 | 含义 | 点一下会怎样 |
|---|---|---|
| 🔔 空心 | 这台设备还没开 | 请求权限并订阅 |
| 🔔 实心 | 已开启 | 关掉（本设备不再收） |
| 🔕 划掉 | 浏览器层面被拒了 | 提示你去浏览器设置里改，页面自己改不了 |

**开关是按设备记的。** 在笔记本上开了，手机上还得再开一次——因为通知是发给具体某台设备的浏览器，不是发给账号的。

**我们不会主动弹权限框。** 一进页面就问"能不能给你发通知"是最招人烦的做法，Chrome 还会因此惩罚站点。必须你主动点铃铛。

### 3.2 四种通知

| 什么时候 | 通知长什么样 |
|---|---|
| **要审批** | **等你批准**<br>给博客站换主题 · 要跑 `rm -rf build` |
| **agent 提问** | **agent 有话问你**<br>给博客站换主题 · 这两个方案你选哪个？ |
| **一轮完成** | **跑完了**<br>给博客站换主题 |
| **一轮失败或被中断** | **这一轮没跑完**<br>给博客站换主题 · 出错了 |

**点一下通知，直接落到那条会话上。** 已经开着的标签页会被切到前台并跳转过去；一个都没开就新开一个。你落地时看到的就是那张等着你点的审批卡片。

**同一条会话只留最新一条。** agent 连着要三次审批，通知栏里始终只有一条，不会堆成一摞。不同会话之间互不影响，各留各的。

**等你动手的两类会挂住不走。**「等你批准」和「agent 有话问你」会一直停在屏幕上，直到你点开或划掉——它们卡着一整轮，错过了 agent 就一直干等到超时。「跑完了」「这一轮没跑完」照旧几秒后自动消失，事情已经结束了，没必要让你一条条去点掉。

> ⚠️ **macOS 上还得改一个系统设置才真挂得住**：Chrome 走系统通知中心，「横幅」样式无论如何都会几秒后自己隐藏。到 **系统设置 → 通知 → Google Chrome → 提醒样式**，从「横幅」改成「提示」。这是系统层面的事，网页代码改不了。Firefox、Safari、Android Chrome 则完全不支持挂住，通知照旧自动消失。

### 3.3 审批通知上能直接点「允许」「拒绝」

不用切回浏览器，通知上就有按钮：

```
┌────────────────────────────────────────┐
│ 等你批准                                │
│ 给博客站换主题 · 要跑 rm -rf build       │
│                                        │
│        [ 允许 ]      [ 拒绝 ]           │
└────────────────────────────────────────┘
```

点完会再弹一条确认：「已允许 / 给博客站换主题 · 要跑 rm -rf build」——**确认里带着
你刚批准的那条命令**，手滑了能立刻看见。

如果这条审批已经不在了（等太久自动拒绝了，或者你在别的设备上刚处理过），会告诉你
「这条审批已经处理过了」，不会静悄悄什么都没发生。

⚠️ **Chrome 只显示两个按钮**。第三个「本会话都允许」被浏览器丢掉了——这是
`Notification.maxActions = 2` 的硬限制。想用它就点开通知主体，页面上的审批卡片三个
按钮齐全。Safari 完全不支持通知按钮，那里只能点开页面处理。

> 这个功能有代价，说在前面：通知栏里只看得到**截断后的**命令（前 100 字），信息比
> 页面上少。长命令、需要看上下文才能判断的，建议点开页面再决定。

### 3.4 你正盯着的那条会话，不会打扰你

**规则很简单：如果此刻你的页面开着、窗口是聚焦的、并且正停在这条会话上，就不发通知。**

因为这时候审批卡片已经在你眼前了，再弹一个系统通知纯属重复。切走、锁屏、最小化、切到别的会话——任何一种情况下你都不算"在看"，通知照发。

这条规则是**跨设备**的：你在笔记本上正看着这条会话，手机上也不会响。

### 3.5 别的会话出了事，照样通知得到

这是推送比"页面内提示"强的地方。页面一次只连着一条会话的实时流，但**通知是服务端直接发到设备的，不经过页面**。所以：

- 你在看会话 A，会话 B 要审批 → 你会收到 B 的通知。
- 你把整个浏览器都关了，三条会话陆续跑完 → 三条通知都收得到。

### 3.6 排队中的消息不会提前报"跑完了"

你在一轮跑着的时候又发了几条消息，它们会[排队](../terms.md)等下一轮。这种情况下，**中间每一轮结束都不发"跑完了"**——只有队列清空、真的没活了才发。否则你会被连着叫醒五次，每次回来都发现它又开始跑下一条了。

### 3.7 电脑上能收，iPhone 上收不到

| 设备 | 能不能收 |
|---|---|
| **电脑**（Chrome / Edge / Firefox / Safari） | ✅ 直接开网页就行，浏览器关了也收得到（进程还在后台时） |
| **Android**（Chrome） | ✅ 直接在浏览器里开就能收 |
| **iPhone / iPad**（Safari） | ❌ 收不到，铃铛显示为「这台设备不支持」 |

**为什么 iPhone 收不到**：iOS 的网页推送只对"添加到主屏幕"装成独立应用的网页开放，而 nimbo chat **有意不做 PWA 独立应用**（2026-07-27 定）。这不是 bug，是一个明确的取舍——想要 iPhone 通知的话，补一个 `manifest.webmanifest` 加两个图标即可，见[技术方案附录 B.5](../tech/push-notification.md)。

### 3.8 通知内容会带上你的命令和问题——但外人看不到

通知正文里有会话标题、要跑的命令、agent 问的问题。这些内容会经过浏览器厂商的推送服务（Chrome 走 Google 的，Firefox 走 Mozilla 的）中转。

**内容是端到端加密的**——推送服务只负责转发一坨它自己解不开的密文，钥匙只有你的浏览器有。它能知道的只有"这个设备在这个时刻收到了一条推送"，看不到里面写了什么。

即便如此，命令和问题都会**截断**（各留一小段），既是为了通知栏显示得下，也是为了少往外送内容。

### 3.9 没配密钥就等于这个功能不存在

推送需要一对 [VAPID 密钥](../terms.md)。仓库里没配的话：

- 铃铛不显示，页面上看不出有这个功能。
- 服务端一次推送都不发，一行错都不报。
- 其它功能完全照常。

这是有意的——自部署 nimbo chat 的人不该被一个没配好的可选功能拦住。

## 4. 范围与非目标

**这一期做**：Web Push 通道（关掉标签页也收得到）· 四种触发（审批 / 提问 / 完成 / 失败）· 点开跳转到会话 · **通知上直接允许/拒绝** · 前台抑制 · 一个铃铛开关。

**这一期明确不做**（理由与将来怎么做见[附录 A](#附录-a-非目标的详细理由)）：

| 非目标 | 一句话理由 |
|---|---|
| 按事件类型分别开关的设置界面 | 先用四个都开跑一阵，看真实噪音在哪再决定切哪个口子 |
| Telegram / Bark / 邮件等外部通道 | 每加一条通道就多一套凭据和失败模式 |
| 侧栏上"别的会话有新动静"的小红点 | 需要一条用户级的实时流，是另一个机制 |
| 通知历史 / 已读未读 | 通知是转瞬即逝的提醒，账本已经在 `conversation_events` 里了 |
| PWA 独立应用（因此 iPhone 收不到） | 用不上"装成应用"这件事本身；代价只是 iOS 端，电脑端不受影响 |

## 5. 成功标准

1. 关掉 chat 标签页后，agent 要审批时仍能收到系统通知，点开落到那条会话的审批卡片上。
2. 正盯着某条会话时，这条会话的任何事件都不弹系统通知。
3. 同一条会话连续三次审批，通知栏里始终只有一条。
4. 一轮跑着时补发三条消息，全部跑完前不出现"跑完了"，跑完后只出现一次。
5. 不配 VAPID 密钥时，页面上没有铃铛，服务端零报错，其它功能全绿。
6. 撤销浏览器通知权限后，服务端不再向该设备投递，那条失效订阅被自动清掉。

## 附录 A. 非目标的详细理由

### A.1 通知里直接允许 / 拒绝——**已改为做了**

原本列为非目标，2026-07-27 你拍板要做，已落地（[§3.3](#33-审批通知上能直接点允许拒绝)）。

当初否决的三条理由，复盘下来只有一条真站得住：

| 当初的理由 | 复盘 |
|---|---|
| SW 跨源带 cookie 调 API 会静默失效 | **不成立**（在本项目的实际用法下）。dev 模式里 `/api` 由前端 dev server 代理成同源，SW 直接 fetch 就带上登录态。只有将来真拆成两个域名部署才会撞上 |
| 通知正文截断，信息不足以做决定 | **部分成立**。短命令一眼够判断，长命令确实看不全——所以在 §3.3 里明说了"长命令建议点开页面" |
| 误点「允许」= 不可逆地放行一条命令 | **完全成立，这是唯一真实的代价** |

接受这个代价的前提是加了一条兜底：**确认通知里原样带上刚批准的那条命令**，手滑了
能立刻看见。这不能撤销操作，但能让你在第一时间知道发生了什么。

### A.2 按事件类型分别开关

真正的问题不是"能不能配"，而是"哪一类是噪音"——这个答案现在纯靠猜。四类里最可能成为噪音的是「一轮完成」（短任务尤其），但[前台抑制](#34-你正盯着的那条会话不会打扰你)已经吃掉了大部分：真正短的任务你基本都在看着。

所以先全开跑一阵。真嫌吵的话，服务端有一个 `CHAT_PUSH_EVENTS` 环境变量能关掉某几类（见[技术方案](../tech/push-notification.md)），改配置重启即可，不需要界面。等积累到真实反馈，再决定要不要把它做成用户可见的设置。

### A.3 外部通道（Telegram / Bark / 飞书 / 邮件）

外部通道的优势很实在：手机上不用装 PWA，通知也更不容易被系统压掉。

不做是因为**每加一条通道就是一整套东西**：凭据怎么存（是密钥，不是订阅，泄露后果更重）、投递失败怎么重试、用户怎么绑定、绑错了怎么办。而 Web Push 是浏览器原生能力，凭据由浏览器生成、天然按站点隔离、撤销权限即作废——同样的收益，少一整个类别的风险。

先把 Web Push 这条打通、验证四个触发点确实是对的时刻，再考虑要不要开第二条通道。真要加的时候，[发送器](../tech/push-notification.md)那一层是现成的扇出点。

### A.4 PWA 独立应用

原本计划做（`manifest.webmanifest` + 两个图标 + `index.html` 一行 link），**唯一**目的是让 iOS 能收通知——iOS 的网页推送只对"添加到主屏幕"的网页开放。2026-07-27 决定不做：用不上"把网页装成应用"这件事本身，而它的收益仅限 iOS 一端。

代价说清楚：**iPhone / iPad 上收不到任何推送**，铃铛显示为「这台设备不支持」。电脑端与 Android 完全不受影响。

要补回来很便宜，做法见[技术方案附录 B.5](../tech/push-notification.md)。

### A.5 侧栏的跨会话小红点

页面现在只对**当前打开的那条会话**有实时流（一条 SSE 连接）。要让侧栏知道别的会话有新动静，得再开一条用户级的流，或者让现有的流升级成多路复用——这是一个独立的机制改造，跟推送不是一回事。

而且推送已经把这个场景**基本覆盖**了（[§3.5](#35-别的会话出了事照样通知得到)）：别的会话有事，你会收到系统通知。小红点是锦上添花的部分，等有了用户级实时流再顺手加。
