# 优雅关闭与崩溃恢复（使用手册）

> 相关：技术方案见 [../tech/graceful-shutdown.md](../tech/graceful-shutdown.md)，施工进展见 [../plans/graceful-shutdown.md](../plans/graceful-shutdown.md)。
> 依赖/延续：[停止本轮](./turn-abort.md)（本功能整个建在它的[停止](../terms.md)机制上——服务要关闭时，就是替用户按一次停止）· [chat 聊天 webapp](./chat-webapp.md) §已知限制 4（本功能把那条「进程重启会中断进行中的一轮」从「静默卡死」变成「如实交代」）。

这一份是**产品/使用视角**：解决什么问题、用户看得到什么行为、边界在哪。内部实现看 [技术方案](../tech/graceful-shutdown.md)。

## 0. 一句话

服务端进程要关闭时（改代码触发热重载、部署、pod 迁移），把正在跑的[轮](../terms.md)**主动收尾**再退出；万一来不及（进程被强杀），下次启动时把这些没收尾的[孤儿轮](../terms.md)补上收尾标记——两条路都让用户看到「这一轮中断了」，而不是一个永远转圈的「思考中…」。

## 1. 要解决的问题

现状（本功能之前）：进程一死，正在跑的那一轮就**静默消失**，但界面毫不知情。

真实撞到的现象（2026-07-27 用户报告）：开发时改了一行代码 → `node --watch` 重启服务 → 界面上那一轮的「思考中…」**一直转到天荒地老**。用户以为 agent 还在干活，实际上进程早就换了一个，没有任何东西在驱动这一轮。

三个具体后果：

1. **界面撒谎**。转圈的动画表示「正在进行」，而事实是这一轮永远不会再有任何输出。
2. **这个会话从此半残**。前端认为「有轮在跑」，于是之后发的每条消息都被判成[排队](../terms.md)，而排队的消息要等「有一轮收尾」才会被发出——永远等不到。用户发多少条都石沉大海，只在待发区堆着。
3. **历史读不懂**。刷新页面后，时间线停在半句话上，没有任何说明。过几天回来看，完全不知道当时发生了什么。

第 2 条已经由[轮状态快照](../terms.md)修掉（界面会当场回到空闲，见 [chat-webapp §5.1](../tech/chat-webapp.md)）。本功能管的是第 1、3 条：**让中断这件事本身被如实记下来**。

## 2. 用户看得到什么

### 2.1 服务关闭时，这一轮被正常收尾

改代码触发热重载、或者部署一个新版本时，如果正好有一轮在跑：

- 时间线末尾出现一条中性标记：**「服务重启，这一轮已中断」**（不是红色报错——这不是 agent 的故障，也不是你的操作失误）。
- 输入框回到空闲形态，可以立刻发下一条消息。
- 已经产出的内容（文字、工具调用、改过的文件）**全部保留**，和你手动按[停止](../terms.md)一样。
- agent **记得**这一轮做到哪了（它进了[模型上下文](../terms.md)），所以下一条消息可以直接说「接着刚才那步继续」。

**和手动按停止的区别只在文案**：手动按显示「已停止」，服务关闭显示「服务重启，这一轮已中断」。分开是因为用户没按任何按钮，看到「已停止」会困惑「我没停它啊」。

### 2.2 沙盒不受影响

沙盒是跑在别的地方的（E2B / Vercel），进程关闭不动它：

- 文件改动、git 分支、装好的 skill 全都在。
- 下一条消息接着在同一个工作区跑。
- 沙盒按自己的空闲超时休眠，不会因为服务重启就被销毁。

### 2.3 被强杀时，下次启动补上交代

有些关闭方式不给任何机会执行代码：`kill -9`、内存耗尽被系统杀、机器断电。这种情况下那一轮来不及收尾。

**下次服务启动时会扫一遍**，把这些没收尾的轮补上「服务重启，这一轮已中断」标记。所以：

- 你现在手上那些已经卡住的会话，**升级后第一次启动就会被治好**。
- 时间线上会有明确交代，而不是停在半句话上。

这一档有一个诚实的差别：被强杀的那一轮，它已经产出的内容**在时间线上还看得到，但 agent 记不住**（那些内容没能被整理进[账本](../terms.md)的消息里）。所以下一条消息最好把要接着做的事再说一遍，别指望它记得。

### 2.4 关闭期间不再接新活

服务正在关闭的那几秒里，如果你恰好发了一条消息，会收到一个明确的错误（「服务正在重启，请稍后重试」），而不是被静默塞进一个马上就要死掉的进程。刷新页面重发即可。

## 3. 范围与非目标

**做**：关闭前主动中止进行中的轮并等它收尾 · 收尾超时后如实放弃并记日志 · 关闭期间拒绝新的轮 · 启动时给孤儿轮补收尾标记 · 与手动停止区分文案。

**不做**（本期明确排除）：

- **续跑被中断的那一轮**。中断了就是中断了，要继续就发新消息。这与[停止本轮](./turn-abort.md)的非目标一致。
- **跨进程接管**。新进程不会去接管老进程正在跑的轮（那需要把轮的执行状态持久化，是另一个量级的工程）。
- **零中断部署**。本功能保证的是「中断被如实交代」，不是「不中断」。
- **恢复被强杀那一轮的半成品到模型上下文**。见 §2.3 的诚实说明。
- **沙盒侧的清理**。沙盒继续按空闲超时休眠，见 §2.2。

## 4. 成功标准

1. **热重载**：起一轮，跑到中途改一下服务端代码 → 时间线末尾出现「服务重启，这一轮已中断」，输入框回到空闲；服务端日志显示中止了 1 个轮并正常退出。
2. 上一条之后立刻发新消息 → 正常起新一轮，且 agent 的回答体现它记得被中断那一轮做过的事。
3. **Ctrl-C**：起一轮，跑到中途按 Ctrl-C → 同样收尾，进程在几秒内退出（不是立刻，也不是挂住）。
4. **强杀**：起一轮，跑到中途 `kill -9` → 重启服务 → 打开该会话，时间线末尾有「服务重启，这一轮已中断」，输入框空闲。
5. **存量僵尸会话**：升级前就卡住的会话，升级后第一次启动即被补上收尾标记。
6. **关闭期间发消息**：在关闭那几秒内发一条 → 收到「服务正在重启」的提示，不是静默失败。
7. **收尾卡住不拖死重启**：故意让一轮的收尾卡住 → 到达超时上限后进程照样退出，日志说清「有 N 个轮没等到收尾」。
8. **空闲时关闭**：没有任何轮在跑时 Ctrl-C → 立刻退出，不产生任何多余的收尾帧或日志噪音。
