## 0. 一句话

**把 agent 干活时产生的内容，送到正在看的人手上**——单进程下这事根本看不见（进程内一个 EventEmitter 就够），只有跨实例时才需要你装东西。

## 1. 解决什么问题

agent 跑一轮会持续吐内容。产生内容的是**某一个进程**，而想看的人连在**哪个进程**上，你说了不算：

- 用户刷新了页面，负载均衡把他分到了另一个实例；
- 同一个会话开了两个标签页；
- 平台压根不让你把请求固定到某个实例（比如 Vercel）。

流分发就是解决「**产出方和观看方不在一个地方**」。

## 2. 什么时候需要装东西

**大多数情况都不需要。** 只有一档要：

| 部署形态 | 流分发怎么办 | 要装吗 |
|---|---|---|
| ⓪ 本机 CLI | 内置（进程内 EventEmitter） | ❌ |
| ① 同机多进程 cluster | 应用层转发到本机那个进程 | ❌ |
| ② Docker · ③ k8s | 应用层转发（`holder` 里存着可达地址） | ❌ |
| ④a Cloudflare Durable Object | 平台自带，实例内直接出 | ❌ |
| **④b Vercel** | **Redis Streams 广播** | ✅ `@runko/stream-redis` |

**④b 是唯一需要装流分发包的一档**——因为 Vercel 的实例由平台调度，你**没有办法**找到持有者、也就没法转发。其余要么单进程（内置够用）、要么能转发、要么平台白送。

> 六档部署形态的完整说明见 [架构总纲 · 技术方案 附录 B](../../../architecture/tech/agent-kernel.md)。

## 3. 你会看到的行为

- **零配置能跑。** 不配流分发时用内置实现，单进程下完全够用。
- **断线能续上。** 用户刷新页面、网络抖一下，重新连上之后能从断的地方接着看，不会丢中间那段——这条是**接口的硬要求**，不是某个实现的加分项。
- **换实现不改业务代码。** 从内置换成 Redis 只动装配那一处。

## 4. 范围与非目标

**不做的**：

- **不做存储。** 流分发是「发布/订阅」，不是「存/取」。历史内容的事实来源永远是[账本](../../../terms.md)，不是这条流。
- **不保证送达。** 没人在看的时候，内容照样进账本；流分发只负责「正在看的人能看到」。
- **不管鉴权和路由。** 谁能订阅哪个会话、请求怎么落到实例上，是[接入层](../../../terms.md)的事（构建者写）。

## 5. 成功标准

1. 单进程下不装任何东西，直播和断线续传都正常。
2. 换成 `@runko/stream-redis` 之后，**两个实例**上的两个标签页看同一个会话，内容一致、都能续传。
3. 业务代码在两种情况下**完全一样**。
